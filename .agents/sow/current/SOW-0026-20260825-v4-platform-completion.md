# SOW-0026 - v4 platform completion: Windows surface, authorized scratch, FreeBSD durable publication, Rust durability-shape pins

## Lead review rules (user decision, 2026-08-21; overrides SWARM.md)

These rules govern this SOW's review process and override the shared
swarm guide. They are placed at the top so they are re-read after every
compaction. SWARM.md is intentionally not updated: this SOW is the
authority for its own review process.

1. ONE review level only. No level-2 gate, no other models: only five
   reviewers, all on the lead's own model, each holding one disjoint
   aspect of the milestone scope, adversarial mode, running with the
   final-review skill.
2. Spawn all five once at first use; every later round is a message to
   the same agents. Never respawn between rounds; restart them only
   between milestones.
3. The milestone closes only when all five reviewers report no P0-P2
   findings. No reviewer is ever replaced by another model.
4. The Rust implementation is the mandatory baseline for ALL five
   aspects. The two implementations must be identical in logic,
   operation order, system calls, errors, and philosophy; the smallest
   divergence in how a thing is done is a performance and correctness
   red flag. Go must follow exactly what Rust does, while expressing
   that logic in natural, maintainer-grade Go.
5. Aspect split (all aspects are judged against the Rust baseline):
   (1) Rust parity - exact logic, operation order, syscalls, errors,
   mmap-only, memory safety, lifetime, durability/crash semantics;
   (2) Go idioms - identical logic and structure, but written as
   natural Go, never foreign or translated-looking;
   (3) absolute performance - the most performant form possible; even
   a single unnecessary branch, copy, or allocation in the hot path is
   a defect;
   (4) wire format and integrity - on-disk bytes, locking, Go<->Rust
   cross-open interoperability;
   (5) APIs, docs, records - public API, errors, documentation, and
   SOW records in sync with Rust.

### Status (2026-08-26) - work package F (Store split-window seam) started

- Scope (recorded disposition in SOW-0025 milestone 4 slice 4-12A): in Rust every output-builder page operation runs inside `with_output_protection` - the armed worker-session probe spans the page fetch, the caller's mutation, and the ownership re-check (`immutable_output.rs` Store for Builder: update_page/copy_page/inspect_page). Go's OutputBuilder returns the page slice from Update and the caller mutates before RestoreDirty, so the mutation window runs with no armed output region; the session handler gate (worker `sigbus_linux_amd64.s`) verifies the fault address falls inside the armed region, so a fault on an output page during the Go mutation window chains instead of recording a RoleOutput fault like Rust. During worker-session recovery the outer RoleSource probe (recovery/api.go build wrap) does not cover the output mapping's region.
- Design decision (resolved here, recorded for the gate): the "store-side region arm" option from the SOW-0025 disposition (the alternative "InspectPage-style hook" closure shape was rejected because Go closures escape through the tree.Store interface and would add a per-page-op allocation to the writer hot path, violating the absolute-performance floor and the recorded zero-allocation session pins). The OutputBuilder gains one pending armed page window: Update and CopyPage arm the output region before the page fetch, RestoreDirty re-verifies ownership and releases the window after the caller's mutation; every store entry point consumes an aborted window first, and Close consumes before unmapping. Go has no RAII drop, so the release point of an aborted mutation is the next store operation or Close (recorded deviation: the Rust closure drop disarms at the error return; the Go pending window stays armed until the next store op - only reachable on already-failing mutation paths, bounded by builder lifetime). On the success path the window is exactly Rust-shaped: armed at op entry, released at the re-check.
- Success-path parity: Update/CopyPage arm (EnterProbe, RoleOutput) before the fetch, RestoreDirty releases (RestoreProbe restores the outer registration, e.g. the recovery build's RoleSource probe), exactly like Rust with_output_protection nested inside enter_source. Library mode (no session): the guard is the inert zero value, no behavior change, no allocation; the existing writer zero-alloc pins stay.
- The DraftStore and selectedStore stores are untouched: Rust draft_store has no per-op probes either (the live writer never runs under a session), so the seam is OutputBuilder-only.
- Inspect joins the same window (Rust inspect_page runs the inspection closure inside with_output_protection): the output region is armed before the fetch and released at the next store operation or Close, so a fault while the caller decodes the returned page records with the Output role. The continuous coverage from one store operation to the next (instead of Rust's per-op closed windows) is the same accepted no-RAII consequence, and the gaps it covers contain no output-mapping touches in compliant code.
